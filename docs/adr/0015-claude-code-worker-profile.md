# 0015 — Claude Code worker profile

- Status: Accepted by the owner on 2026-09-15 for implementation under [issue #13](https://github.com/gsornsen/anastom/issues/13); native and authentication gates remain open
- Date: 2026-09-15

## Context

M2 proves one unchanged Markdown Task across Pi and Codex. M2.5 should exercise that same control-plane contract through Claude Code without turning Claude-specific configuration, sessions, or transcripts into workflow authority. The owner prefers subscription-authenticated usage if the official interface and terms support it. A shared path-policy API should be informed by this third real adapter rather than designed around only Pi/Codex cases.

## Proposed decision

Invoke an operator-installed, unmodified `@anthropic-ai/claude-code@2.1.268` CLI binary in non-interactive `-p` mode. The [official setup guide](https://code.claude.com/docs/en/setup) says the npm package installs the native binary through a matching platform dependency. Anastom should attest the exact official package, platform, version, and executable before use; it should not bundle or modify Anthropic's proprietary binary in AGPL artifacts. Own a fresh process group per attempt, bounded JSONL from `--output-format stream-json --verbose`, and final `--json-schema` output. Select the model explicitly outside the authored Task; record that identity as configured until native evidence confirms effective resolution. Use `--safe-mode` to suppress user/project customizations while retaining normal authentication, `--restricted` for working-directory file-tool confinement, `--strict-mcp-config`, no session persistence, a fixed built-in-tool allowlist, and `dontAsk` permissions. Avoid Bash in the initial worker profile; the control plane runs the authoritative verifier. The [CLI reference](https://code.claude.com/docs/en/cli-usage) and [programmatic guide](https://code.claude.com/docs/en/headless) describe these controls. Exact combinations, file-tool behavior, JSONL framing, and descendant cleanup remain native feasibility gates before a live call.

Propose runtime ID `claude-code`, paired `--provider anthropic --model <id>`, and an explicit `--auth-source subscription|api-key` selection with no implicit default. No Task schema or runtime-contract type changes are needed merely to name this adapter. The implementation review should challenge whether `--auth-source` belongs at the CLI selection boundary before cementing it as public API. The adapter must reject an observed credential source other than the selected one before run state is created; it must not silently fall back from subscription to API billing. Both modes must use the end user's own Anthropic-authenticated, unmodified CLI. Anastom provides no Claude.ai sign-in flow, reads no OAuth/keychain values, proxies no model requests, and intermediates no usage or charges.

The [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk) says third-party developers may not offer claude.ai login or rate limits in their products without prior approval. Anthropic's more specific [Claude Code legal and compliance guide](https://code.claude.com/docs/en/legal-and-compliance) also says an end user may sign in to the **unmodified Claude Code binary** with their own subscription, even when a platform hosts it. It forbids third-party apps from offering their own Claude.ai login or routing Free/Pro/Max credentials on users' behalf; it also prohibits collecting or intermediating tokens and requires each end user to authenticate and be billed directly. The [programmatic guide](https://code.claude.com/docs/en/headless) documents `claude -p`, and Anthropic's [June 15 pause notice](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) says it and third-party usage currently draw from subscription limits. **Design inference, for owner review:** Anastom can offer a local-direct profile that invokes the end user's separately installed and authenticated, unmodified CLI without offering a login, proxying requests, or intermediating plan credentials. Whether a redistributable automation adapter counts as prohibited routing "on behalf of" users is not resolved by these pages; do not treat free distribution as an exemption. The [authentication guide](https://code.claude.com/docs/en/team) explains that ambient API keys can take precedence over subscription login in print mode, so the selected source needs model-free verification. [Bare mode](https://code.claude.com/docs/en/headless) excludes OAuth/keychain login and cannot implement the subscription profile.

Implementation refinement after the owner's design acceptance: keep `--auth-source` at the CLI selection boundary because billing source, like model selection, is operator choice rather than authored Task state. The subscription profile uses `--safe-mode --restricted` and accepts only first-party personal Pro/Max status while rejecting ambient key/provider overrides. The API-key profile instead uses `--bare --restricted` with an operator-provided environment key; Anthropic documents that bare mode does not read OAuth/keychain login. Native localhost evidence for the pinned release showed bare mode exposed only Read/Edit despite a requested Read/Glob/Grep/Write/Edit set, so the API-key profile is explicitly limited to editing existing files and cannot claim creation through Write. The common runtime contract has no individual tool-capability field; this limitation is documented at the package/CLI selection boundary rather than encoded as a new contract field before a cross-runtime need is established. The owner must review this scope change before milestone acceptance.

`--safe-mode` still applies administrator-managed policy settings. [Settings precedence](https://code.claude.com/docs/en/configuration) places managed policy above flags, and [server-managed settings](https://code.claude.com/docs/en/server-managed-settings) may refresh asynchronously. An offline local loopback request does not prove the behavior of a subscription or managed organization. Before live use, require model-free evidence of effective policy or a reviewed fail-closed profile that proves conflicting managed instructions, tools, hooks, and permissions cannot cross the worker boundary. If the pinned release cannot establish this, revise the interface choice instead of bypassing the gate.

The implementation gate rejects Claude Code endpoint-managed files, matching macOS managed-preference files, or a nonempty effective `com.anthropic.claudecode` domain. Unreadable or unrecognized inventory rejects. It limits subscription support to Pro/Max personal plans, for which Anthropic says remote Team/Enterprise settings delivery is unavailable. The owner machine has unrelated configuration profiles; `profiles show -all` requires root, so the gate uses effective domain/file inspection instead of inspecting all profile payloads. The gap between that model-free OS evidence and a future policy refresh remains an explicit owner-review limit. Native fake managed-policy fixtures cannot stand in for remote managed settings.

## Interface comparison

| Boundary           | Direct CLI `2.1.268`                                                                                                                                                                                  | Agent SDK `0.3.273`                                                                                                                                                                                                                              |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Launch and cleanup | Anastom owns argv, JSONL limits, and the POSIX process group directly. Native cancellation and descendants still need deterministic tests.                                                            | Published declarations expose `spawnClaudeCodeProcess`, `SpawnedProcess`, an `AbortController`, and `Query.close()`; a custom process owner could satisfy the contract, but safe termination is not guaranteed merely by `close()` returning.    |
| Configuration      | `--safe-mode` suppresses ordinary customizations and keeps normal auth; administrator policy still applies.                                                                                           | `settingSources: []` excludes user/project/local sources but not managed policy. `resolveSettings()` is alpha and explicitly omits `policyHelper` execution and fresh server-managed payload unless supplied.                                    |
| Output and usage   | Native JSONL plus `--json-schema` can expose a final structured report and result usage. Anastom must bound frames and validate the report again.                                                     | Typed messages and structured output reduce parsing; `SDKResultMessage` offers cumulative usage and per-model fields, but the current published declarations do not by themselves prove missing-counter semantics or bounded transport behavior. |
| Authentication     | Uses the end user's installed CLI and its credential precedence. The proposed direct subscription mode never offers login or handles tokens; the interpretation of automated invocation needs review. | The SDK overview expressly warns third-party developers against offering Claude.ai login/rate limits; bundling its binary does not settle that boundary.                                                                                         |

The SDK comparison used the official registry archive `@anthropic-ai/claude-agent-sdk@0.3.273`, whose SHA-512 matched registry `dist.integrity`; its `package.json` declares bundled Claude Code `2.1.273`. This is a source/interface comparison, not a claim that the SDK lacks process control. A later release or a proven SDK transport may justify revisiting the choice.

## Native evidence and limits

The checked-in [offline CLI probe](../../scripts/probe-claude-cli.ts) ran the owner's installed native `2.1.268` binary against an ephemeral `127.0.0.1` fixture with a synthetic API key and no real model call. The probe did not open or copy credential-store values. With `--safe-mode --restricted`, neither user/project `CLAUDE.md` sentinel entered the two observed model requests, and the project hook marker was absent. The native `StructuredOutput` tool returned schema-valid JSON and a successful result. The fixture observed two local `POST /v1/messages` requests despite `--max-turns 1`; their cause is not established and the test does not infer real billing or retry rates. [M2.5 feasibility](../M2_5_FEASIBILITY.md) records the exact executable hash, command, result shape, and unproved boundaries.

## Compatibility and path-policy review

Keep the existing `RuntimeAdapter` lifecycle, selected-capability preflight, event history, independent verifier, and owned artifacts. Only public identity, token counters whose semantics are established, bounded logs, and terminal evidence cross the adapter. Original M1/M2 stores must replay without rewriting rows. No routing, fallback, recovery, multi-worker orchestration, or model-cost policy enters M2.5.

Implementation should record Claude-specific path cases: end-user-installed executable, managed-policy inventory, workspace-constrained native file tools, and durable run artifacts. The implemented profile places the bounded schema on the CLI and pipes context through stdin, so it creates no temporary prompt/schema file. Extract shared path-policy operations only where at least two concrete consumers require the same root, symlink, file-type, and lifetime rules. Keep operator-selected Task paths distinct from worker-relative paths. [ADR 0016](0016-path-policy-after-third-adapter.md) compares the concrete cases and proposes a separate narrow follow-up rather than cementing a catch-all API in M2.5.

The design PR changes no worker package or public API. The owner reviewed and approved this ADR and the [M2.5 build brief](../M2_5_BUILD_BRIEF.md) on 2026-09-15, satisfying issue #13's design-review gate before adding the production adapter. Approval of the design does not establish the native feasibility gates or authorize a live demonstration.
